Графовая память для Claude на своём сервере

Как мы построили многослойную память на Graphiti + FalkorDB, загрузили в неё 3,6 тысячи фрагментов заметок и переписки, собрали всё в один граф и какие грабли собрали по дороге. Всё ниже проверено на живом сервере 15 сентября 2026 года; цифры настоящие.

Зачем и что получилось

У ассистента уже была файловая память: markdown-заметки, которые он читает в начале сессии. Она мгновенная и надёжная, но плоская: нет поиска по смыслу, нет связей между объектами, нет понимания, что факт устарел. Хотелось второй слой поверх файлов.

Graphiti (getzep/graphiti, Apache-2.0) строит из текста темпоральный граф знаний: карточки-сущности, факты-рёбра между ними, у каждого факта две даты — с какого момента он верен и с какого перестал. Модель нужна только при записи; поиск работает на эмбеддингах, полнотексте и обходе графа без модели. Есть готовый MCP-сервер, так что Claude Code видит граф как набор инструментов.

Что в итоге лежит в графе (редакция от вечера 15.09, после сборки единого графа main): 46 файлов памяти боевого сервера, 254 файла памяти старого сервера, 49 транскриптов сессий за июнь–июль, 40 транскриптов с боевого сервера и 20 заметок из inbox-бота. Итого 3608 фрагментов, 7,7 тысяч карточек, 33,7 тысяч фактов в одном графе. Стоимость всего дня по ключу — около 40 долларов вместе с пилотами, утренней загрузкой по группам и вечерней пересборкой в один граф; повторная сборка с нуля по отлаженному конвейеру стоила бы 20–25.

Итоговая архитектура

контейнер graphiti-mcp
образ zepai/knowledge-graph-mcp: FalkorDB + MCP-сервер в одном. Порты только на 127.0.0.1: 6379 (база), 8000 (MCP, endpoint /mcp без слэша), 3001 (веб-просмотр графа).
модель извлечения
google/gemini-2.5-flash-lite через OpenRouter. Читает фрагмент, выдаёт карточки и факты по JSON-схеме.
модель дедупа
anthropic/claude-sonnet-5 (с 16.09; до этого Haiku 4.5) — то, что graphiti-core зовёт small_model. Решает «эта карточка уже есть?» и «этот факт противоречит старому?» — по нашим промптам (см. «Аудит»).
эмбеддер
BAAI/bge-m3 (1024 измерения). Для массовой загрузки — через OpenRouter, для повседневной работы MCP — локальный контейнер TEI на CPU. Векторы идентичны.
группы
В Graphiti group_id — пространство имён; в FalkorDB каждая группа — отдельный граф. Поиск умеет по списку групп, а связи и устаревание работают только внутри одной. Поэтому в итоге у нас один граф main — группа по умолчанию MCP: поиск и запись без group_ids (см. «Единый граф»).
патчи в MCP-сервере
Те же monkeypatch, что у загрузчиков, подключены к процессу MCP через sitecustomize.py (PYTHONPATH=/app/loaders, GRAPHITI_PATCH=1). Без них поиск по большому графу висит минуты и вешает базу.
загрузчики
Свои скрипты на graphiti-core (add_episode_bulk), минуя очередь MCP: 12 фрагментов за порцию, 60 потоков, патч с векторным индексом.
наши правки
Ни одной строчки внутри Graphiti не менялось. Всё — monkeypatch поверх (см. «Скорость») и обёртки. Обновление версии ничего не ломает: патч откатывается на штатное поведение при ошибке.

Установка

  1. Compose. Один сервис из готового образа, порты привязать к 127.0.0.1, том для данных базы включить в ночной бэкап. Каталог со своими скриптами монтировать как каталог (./tools:/app/loaders:ro), не отдельными файлами.
  2. config.yaml. Провайдер LLM — openai с OPENAI_API_URL OpenRouter: для неофициального URL graphiti берёт совместимый клиент через chat.completions. Родной клиент anthropic в образе сломан (лишний аргумент temperature). Типы сущностей — свои, doc-only: Server, Service, Project, Domain, Incident, Credential, Runbook, Rule, Human, Company, Tool. Имена, совпадающие с встроенными (Person, Organization, Document…), подтягивают rich-модели и по отдельному вызову модели на каждую карточку — в семь раз дороже.
  3. Телеметрия выключена (GRAPHITI_TELEMETRY_ENABLED=false), SEMAPHORE_LIMIT для MCP — 5–8.
  4. Фаервол. Помимо привязки к localhost добавить порты в правила ip6tables-DROP: у нас утром аудит нашёл, что IPv6 обходил все ограничения.
  5. Регистрация в Claude Code: claude mcp add --transport http --scope user graphiti http://127.0.0.1:8000/mcp. Инструменты mcp__graphiti__* появятся в новых сессиях.
  6. Патчи и в MCP-сервер. В compose: PYTHONPATH=/app/loaders, GRAPHITI_PATCH=1, VECTOR_INDEX=1; в каталоге скриптов лежит sitecustomize.py, который импортирует патчи в любой python-процесс контейнера. Проверка: в логах контейнера строка falkor_vector_patch: … подменено в 9 местах. Симптом без патча на графе в 30 тысяч фактов: search_memory_facts не отвечает больше двух минут, один поток FalkorDB на 100 %, база не отвечает даже на PING.
  7. Свой стартовый скрипт контейнера. Штатный /start-services.sh ждёт от redis-cli любой ответ, а при снимке в сотни мегабайт база отвечает LOADING: MCP стартует раньше базы, падает, контейнер уходит в цикл рестартов, и загрузка снимка каждый раз начинается заново. Копия скрипта с ожиданием именно PONG монтируется поверх (entrypoint: ["/bin/sh","/start-services.sh"]). Загрузка снимка на 360 МБ — около минуты.
  8. Учёт расходов. OpenRouter отдаёт точную цену ответа только с флагом usage.include, который Graphiti не ставит. Мы подняли крошечный прокси, дописывающий флаг и пишущий цену каждого вызова в JSONL. Для массовой загрузки прокси потом убрали (см. «Скорость»), для MCP оставили — объёмы там малы, а учёт полезен.

Что важно знать про Graphiti

Внутри graphiti-core две роли: основная модель извлекает карточки и факты, а small_model делает дедуп и инвалидацию. По умолчанию это одна модель. Мы проверили три варианта дедупа на тех же 37 фрагментах: flash-lite оставила мусорные «серверы» вроде eth0 и путей к файлам, gemini-2.5-flash наплодила дублей людей, Haiku 4.5 дала самый чистый результат при той же скорости. Итог: дешёвая модель на извлечение, Haiku на дедуп.

Что не лечит ни одна модель: «Амстердам», «прод» и «201.51.23.17» так и остаются тремя карточками. Кандидатов на склейку Graphiti ищет по похожести имён, и такие пары до модели просто не доходят. Для этого нужен пост-проход по таблице псевдонимов (см. «Качество»).

Эмбеддер

На один фрагмент Graphiti делает 3–5 вызовов модели и 50–100 вызовов эмбеддера: каждая карточка, каждый факт, каждый поисковый запрос дедупа. Поэтому задержка эмбеддера определяет всё.

Грабля

Локальный и облачный bge-m3 дают одинаковые векторы (косинус 1,0000 на проверке), их можно смешивать в одном графе. А вот смена модели эмбеддера — это другое пространство координат: граф придётся перезалить целиком.

Скорость: где на самом деле тормоз

Это главная глава. Утренняя загрузка шла по 200–490 секунд на порцию из 12 фрагментов и замедлялась с ростом графа; к вечеру те же порции шли за 80–120 секунд и не зависели от размера. Между этими цифрами — пять находок, каждая из которых казалась «той самой».

1. У драйвера FalkorDB в graphiti-core нет векторного индекса

Драйвер создаёт только range- и fulltext-индексы. Каждая проверка «есть ли похожая карточка» — это vec.cosineDistance в WHERE по всем узлам группы: полный перебор, 120–140 мс на запрос при 3 тысячах фактов, десятки запросов на фрагмент. База ела 3–8 ядер, порции росли линейно с графом. Это видно в GRAPH.SLOWLOG.

FalkorDB при этом умеет HNSW-индекс из коробки. Мы написали патч (tools/falkor_vector_patch.py), который лениво создаёт два индекса в графе группы и подменяет четыре функции graphiti-core на версии с db.idx.vector.queryNodes / queryRelationships. Паттерн подсмотрен в стороннем форке (JeremyErard/sdi-graphiti-service, PR #58). Замер: перебор 140 мс → индекс 1,5 мс.

CREATE VECTOR INDEX FOR (n:Entity) ON (n.name_embedding)
  OPTIONS {dimension:1024, similarityFunction:'cosine'}
CREATE VECTOR INDEX FOR ()-[e:RELATES_TO]-() ON (e.fact_embedding)
  OPTIONS {dimension:1024, similarityFunction:'cosine'}
Грабля внутри грабли

Первая версия патча подменила метод класса FalkorSearchOperations. В 0.30.x этот класс в пути дедупа не участвует: реальные реализации — функции-модули в search.search_utils, реэкспортированные по имени в search.search и utils.maintenance.node_operations. Подменять надо во всех модулях, где лежит оригинал. Патч честно отработал вхолостую: индексы не создались, время не изменилось.

Грабля: как искать концы ребра

Наш первый запрос брал кандидатов из индекса и потом искал ребро по uuid: MATCH (n)-[e:RELATES_TO {uuid: rel.uuid}]->(m). FalkorDB на такой связке перебирает все карточки на каждого кандидата: 1640 мс, хуже штатного перебора. Правильно — startNode(e) / endNode(e): 1 мс. Ровно этот дефект есть и в штатном полнотекстовом поиске рёбер graphiti-core 0.30.1 (1040 мс), в 0.30.2 его починили той же формой запроса; мы перенесли исправление в патч. Поиск рёбер по списку uuid тоже переписали: UNWIND $uuids AS u MATCH ()-[e {uuid:u}]->() без меток на концах идёт по индексу (0,7 мс), с метками — 250 мс.

2. Загрузчик слал эмбеддинги не туда

В загрузчике памяти база для эмбеддера была взята из переменной для модели. Итог: 20 тысяч вызовов bge-m3 ушли в облако через прокси вместо локального контейнера, при медиане 0,5 с и одном зависании на 136 секунд, которое держало всю порцию. Ошибка нашлась только по журналу задержек прокси. Мораль: печатать в логе загрузчика, куда именно идут эмбеддинги.

3. Локальный эмбеддер не тянет массовую загрузку

Как только эмбеддинги пошли в локальный TEI, он упёрся в 6 ядер: очередь 3–4 с, при двух загрузчиках 429. Плюс лимит 32 текста на запрос, а пакетный путь Graphiti шлёт по 35–45 (обёртка embed_chunk_patch.py режет по 32). Решение: массовая загрузка — облачный bge-m3 напрямую, локальный — только для MCP.

4. Прокси без keep-alive

Учётный прокси открывал новое TLS-соединение на каждый запрос: 594 мс против 400 мс у SDK с постоянным соединением, то есть плюс 30–50 % на каждый из тысячи вызовов на порцию. «Размышления» модели, которые прокси выключал, у flash-lite и так выключены (9 вызовов из 8 тысяч с reasoning-токенами). Массовую загрузку перевели напрямую в OpenRouter; таймауты (модель 120 с, эмбеддер 20 с) и повторы выставлены в SDK-клиенте, который передаётся в конструкторы graphiti (OpenAIGenericClient(client=…), OpenAIEmbedder(client=…)).

5. Потоки, порции, соединения

  • 60 потоков (SEMAPHORE_LIMIT) с пулом соединений к базе 512 → «Too many connections» на каждой порции. Пул нужен 4096 (свой клиент FalkorDB с max_connections).
  • Порция 25 фрагментов → дедуп-запрос на 600+ карточек, ответ модели за 8 тысяч токенов рвётся, JSON не парсится, повторы по кругу, порция не заканчивается никогда. Порция 12 — потолок для flash-lite.
  • Больше 60 потоков не помогает: внутри порции параллельность ограничена числом фрагментов. Единственный множитель — несколько процессов на разные группы (у нас три группы транскриптов параллельно: 1805 фрагментов за 80 минут).
  • После всех правок база почти простаивает (4,5 мс на запрос), а порция целиком — это ожидание сети умножить на последовательные фазы Graphiti: извлечение → дедуп карточек → дедуп фактов, каждая ждёт все ответы.

Загрузка корпуса

Файлы памяти режутся на фрагменты до 2500 символов по границам абзацев; у фрагмента reference_time = дата изменения файла (для перевезённого архива — из сохранённого манифеста, иначе всё датировалось бы днём копирования). В шапке фрагмента — описание файла и, для исторических, баннер «архив до переезда, роли серверов действовали до такой-то даты»: модель переносит это в даты фактов.

Транскрипты сессий Claude Code (JSONL) — только реплики человека и текстовые ответы ассистента: без вызовов инструментов, их выводов, «размышлений», системных вставок и вставок скиллов (одна такая вставка была на 560 тысяч символов). Реплики длиннее 40 тысяч символов выбрасываются. Куски режутся по границам реплик, reference_time — время первой реплики куска, в шапке — тема сессии и дата.

Инструкция модели

Через custom_extraction_instructions: IP, hostname и прозвище одной машины — одна карточка; не делать карточек из путей, кодов ошибок, переменных, портов, интерфейсов; значения секретов не извлекать; даты вида 14.09 относить к текущему году; ассистента не делать субъектом фактов; invalid_at ставить только при явном «закрыто / больше не / до даты». Без последнего пункта модель штамповала «устарело» на треть фактов, включая живые.

Идемпотентность: список загруженных имён фрагментов хранится в state/<группа>.json; для докачки имя включает хеш содержимого (файл#3@a1b2c3d4), так что изменённый кусок грузится заново, а прежняя версия остаётся историей. На группу — один загрузчик (flock): два писателя в один граф плодят дубли.

Фильтр секретов

Транскрипты полны токенов, паролей и строк подключения в выводах команд. Перед загрузкой каждая реплика проходит три слоя:

  1. Словарь реальных значений, собранный с самого сервера: env-файлы, ключи, приватные ssh-ключи, JSON с credentials. Около 200 значений, живут только в памяти процесса. Точное совпадение → [REDACTED:known].
  2. Регулярки по форматам: ключи OpenRouter/OpenAI/Anthropic, токены Telegram-ботов, JWT, Google, VK, вебхуки Bitrix, PEM-блоки, user:pass@ в URL, Bearer, KEY=VALUE с секретным именем ключа, телефоны.
  3. Энтропия: длинные (≥24) высокоэнтропийные токены без пробелов и точек.

Проверка — повторный прогон фильтра по выходу, ожидается ноль. Пять итераций правок ушло на ложные срабатывания: имена файлов памяти вида project_x_2026-07-11, слово «passport» как «pass», кириллические описания из комментариев в env, имена ботов после слова «токен», имена моделей vendor/model.

Грабля

Фильтр стоял на транскриптах, а память старого сервера считалась чистой (секреты из неё вынесли заранее). После склейки карточек в сводке «Владелец» всплыл телефон старого Telegram-аккаунта. Написали второй инструмент — прогон того же фильтра по содержимому графа (сводки, факты, тексты эпизодов) с записью обратно: исправлено 213 полей, среди них 24 телефона, ключ IndexNow, старые вебхуки, строки подключения. Правило: любой источник — через фильтр, после загрузки — контрольный прогон по графу.

Качество и пост-проходы

Что получилось хорошо

Факты датированы временем сессии или файла; инфраструктурные факты точны («IP Алматы нужно добавить в allow-list Selectel», «на nspd-proxy2 включён парольный SSH»); история проекта восстанавливается по датам («у НСПД нет point-identify API» — 13 июля).

Что лечится пост-проходом

merge_aliases.py — склейка внутри графа: таблица псевдонимов (IP ← прозвища, хосты, Tailscale-адреса; «Владелец» ← имя, ник, chat_id; «Claude Code» ← Claude, Ассистент), IP с портом или /32 → голый IP (кроме 127.0.0.1 и 172.17.0.1, где порт — это разные сервисы, и кроме подсетей /24), одинаковые имена одной метки без учёта регистра. Рёбра перевешиваются с копией всех свойств (SET r2 = properties(r) сохраняет и uuid, и векторы — проверено векторным запросом), упоминания из эпизодов переносятся, сводки склеиваются, дубль удаляется. Перед боевым прогоном — GRAPH.COPY и проверка на копии. У нас: перевешено 2812 рёбер, потерянных ссылок из эпизодов ноль.

Что остаётся

  • Доля фактов с invalid_at 20–37 %. Это не только модель: Graphiti гасит старый факт при появлении похожего нового (темпоральное вытеснение), для истории это правильно. При поиске смотреть на даты, а не отбрасывать.
  • В транскриптах ассистент местами остаётся субъектом («Claude Code выявил…»).
  • Файл памяти про саму эту систему даёт мета-факты («mail.ewa.pro распознан graphiti как сущность»). Такие файлы лучше исключать из загрузки.

Эксплуатация

  • Поиск в сессии: search_memory_facts и search_nodes без group_ids — всё в main; факты идут с valid_at/invalid_at. Половина фактов в едином графе помечена как устаревшие: Graphiti гасит старый факт, когда приходит похожий новый (так и должно быть для истории), поэтому устаревший факт — не мусор, а «как было тогда». Запись в конце сессии — add_memory одного-двух выводов, полминуты и копейки. Ответ поиска на графе в 34 тысячи фактов — 0,2–1,3 с.
  • Ночная докачка кроном в main: изменённые файлы памяти через фильтр (имя фрагмента с хешем содержимого и статуса), дайджесты сессий, не менявшихся ≥2 часов, тексты из inbox-бота; после — склейка псевдонимов, контроль секретов, снятие однодневных окон, метрики качества; в Telegram — только при ошибках, секретах или метриках вне нормы.
  • Сторож долгих загрузок: скрипт раз в две минуты проверяет живость процесса, застой более 10 минут и новые ошибки порций, раз в 20 минут даёт сводку. Загрузка идемпотентна, перезапуск теряет одну порцию.
  • Добивка после сборки. Порция может сорваться (модель вернула битый JSON после всех повторов) — её фрагменты не попадают в журнал загруженного. Повторный прогон загрузчика по тем же файлам грузит только их (у нас после сборки таких оказалось 120 из 3600), затем склейка и контроль секретов ещё раз.
  • Снимок перед разрушительным. Перед удалением графов и пересозданием контейнера — redis-cli SAVE и копия dump.rdb из тома в каталог снимков (права 600). Откат — положить файл обратно в том и перезапустить контейнер. Том FalkorDB также в ночном rclone; граф в любой момент можно пересобрать из файлов и отфильтрованных транскриптов.
Две грабли про сам сервер

Bind-mount одного файла в Docker держит старый inode: после правки редактором контейнер видит прежнюю версию. Монтировать каталог. И второе: правка работающего bash-скрипта не действует — файл меньше 8 КБ bash читает в буфер при старте целиком. Наш цикл «три группы параллельно» так и запустил две. Перезапускать.

Все грабли одним списком

  1. Родной клиент anthropic в образе MCP сломан → OpenAI-совместимый путь через OpenRouter.
  2. Встроенные имена типов сущностей включают rich-модели → отдельный вызов на карточку, в 7 раз дороже. Свои doc-only имена.
  3. Удалённый эмбеддер с задержкой 1,8 с → 180 с на фрагмент. Задержка эмбеддера решает всё.
  4. Инструкция «устарело → invalid_at» слишком буквальна → треть фактов проштампована. Только при явных словах.
  5. Нет векторного индекса у драйвера FalkorDB → перебор, база ест ядра, порции растут с графом. Патч с HNSW.
  6. Патч подменил не тот класс → работал вхолостую. Подменять функции во всех модулях-импортёрах.
  7. Поиск ребра по uuid после индекса → 1640 мс. startNode/endNode → 1 мс. Тот же дефект в штатном fulltext 0.30.1.
  8. Эмбеддинги памяти шли в облако через прокси по ошибке в переменной.
  9. Локальный TEI на CPU: 429 и лимит 32 текста на запрос при массовой загрузке.
  10. Прокси без keep-alive: +30–50 % на вызов. Напрямую, таймауты в SDK.
  11. 60 потоков и пул 512 → Too many connections. Пул 4096.
  12. Порция 25 → ответ дедупа рвётся по лимиту вывода, бесконечные повторы. Порция 12.
  13. RediSearch: Syntax error в полнотекстовом запросе роняет всю порцию → оградить, отдавать пустой список.
  14. Bind-mount файла держит старый inode; правка работающего bash-скрипта не действует.
  15. Дубли «прод / IP / город» не лечит ни одна модель → таблица псевдонимов.
  16. Секреты в «чистой» памяти → фильтр на всё и контрольный прогон по графу.
  17. Мелкие группы ради скорости → швы между графами. С индексом размер группы не важен; группы делить по смыслу, не по скорости. В итоге — один граф.
  18. MCP-сервер без патчей на большом графе: поиск висит минуты, FalkorDB перестаёт отвечать на PING. Патчи через sitecustomize.py и в MCP.
  19. Штатный старт контейнера принимает LOADING за готовность → цикл рестартов, снимок грузится заново каждый раз. Ждать именно PONG.
  20. Фильтр служебных строк лога по подстроке «Unterminated» глотал и строки ошибок порций → сторож видел 1 сбой из 9. Строки !! batch пропускать всегда; в логах с выводом модели grep только с -a.
  21. GROUPS в bash — встроенный массив; переменную с таким именем сторож молча читал как «0».
  22. pkill -f имя_скрипта из оболочки, в командной строке которой есть то же имя, убивает саму оболочку. Убивать по PID.
  23. Bind-mount одного файла: если файл на хосте переехал и на его месте появился каталог, контейнер после рестарта не поднимется вовсе. Монтировать каталоги.
  24. Дешёвая модель извлечения плодит мусорные карточки Server (IP Telegram, подсети, идентификаторы серверов у провайдера) и новые прозвища одного сервера («Амстердам-как-dev», «будущий dev»). После сборки выгрузить список Server/Human, дописать таблицу псевдонимов, склеить ещё раз.

Единый граф main

Почему один граф, а не склейка семи. Библиотекарь Graphiti работает только в момент записи: видит все карточки и факты того же графа, сливает совпадения по смыслу (не только по имени), пишет сводки нарастающим итогом и ставит invalid_at старым фактам при появлении противоречащих. Ничего из этого не появится задним числом, если механически слить семь готовых графов. Поэтому корпус был перезаписан в один граф.

Как собирали. За основу взяли уже загруженную память старого сервера (самый большой блок, 811 фрагментов): GRAPH.COPY mem_dev main, затем в копии MATCH (n) SET n.group_id='main' и то же для рёбер (Graphiti фильтрует по свойству group_id внутри графа), журнал загруженного скопировали под новым именем. Дальше хронологически и последовательно одним писателем: старые транскрипты (1805) → память боевого сервера (113) → его транскрипты (859) → inbox (20). После каждого блока — таблица псевдонимов, в конце — контроль секретов (нашёл 15 полей, унаследованных из памяти старого сервера, которая утром грузилась без фильтра). Затем добивка сорванных порций (120 фрагментов), дописанные псевдонимы («Амстердам-dev», «будущий dev», «двойник Алматы» и ещё десяток, найденных в списке Server-карточек), ещё одна склейка и контроль (0). Старые графы удалены после снимка базы.

Что дало. Запрос «прод / Амстердам / 201.51.23.17» возвращает одну карточку сервера первой строкой (утром — четыре–шесть). Факт о Selectel-прокси показывает цепочку состояний с датами: июльский сбой, сентябрьские перенастройки, каждое со своим valid_at/invalid_at. Поиск и запись из сессии — без перечисления групп. Цена: половина фактов помечена устаревшими (в графах по группам было 20–37 %) — это следствие того, что один и тот же сервер и одни и те же сервисы упоминаются в сотнях фрагментов за три месяца, и каждый новый похожий факт гасит предыдущий. Для истории это правильно; для «что верно сейчас» смотреть на факты без invalid_at или с самой поздней valid_at.

Что стоило вечера. Первая же проверка поиском через MCP на графе в 30 тысяч фактов повесила базу: MCP-сервер работал без наших патчей и шёл полным сканом с перебором карточек на каждого кандидата. Лечение — патчи через sitecustomize.py в процесс MCP; попутно всплыл цикл рестартов контейнера на большом снимке и невозможность рестарта из-за bind-mount переехавшего файла (см. «Установка» и «Все грабли»).

Аудит качества записи (16.09)

На второй день граф проверили «вслепую»: спросили про проект, о котором память была только в графе. Ответ нашёлся, но выявил три дефекта, которые первый день скрывал за метриками скорости и цены. Ниже — что это было, почему не поймали сразу, и что изменено, чтобы дальше писалось правильно.

1. Уточнение считалось опровержением

Половина фактов графа стояла с invalid_at, а 6,3 тысячи «прожили» меньше суток. Причина — по коду graphiti-core 0.30.1 (апстрим main идентичен): custom_extraction_instructions доходит только до извлечения; дедуп карточек (dedupe_nodes) и разбор противоречий (dedupe_edges.resolve_edge) идут по встроенным промптам, которые наших правил не видят. А в штатном промпте противоречий стоит пример «engineer → senior engineer = противоречие». Пересказ того же факта в соседнем куске сессии гасил предыдущий.

Почему не поймали в первый день

Проблему видели дважды («пере-инвалидация 399 из 1294», «50 % с invalid_at — темпоральное вытеснение, для истории отчасти правильно») и оба раза объяснили, а не разобрали. Смягчённая инструкция «дала» на пилоте из 12 фрагментов почти ноль погашений — на пустом графе нечему противоречить, тест ничего не проверял. Урок: настройку, которая «должна» влиять, проверять по коду — куда она реально попадает.

Лечение. Промпты дедупа подменены своими через тот же sitecustomize, что и векторный индекс (prompt_patch.py): противоречие — только когда оба факта не могут быть верны одновременно (другой порт, другой сервер, включено→выключено, явное «больше не / удалён / заменён»); уточнение, деталь, перевод, другой аспект, план и его результат — не противоречие; при сомнении — ничего не гасить. В промпт карточек: однофамильцы с разной ролью — разные люди; нарицательное («бот», «банк», «сервер») без указания, какой именно, — не склеивать ни с чем. На дедуп поставлена сильная модель (Sonnet 5, ≈1,1 ¢ за кусок против 0,8 ¢ на Haiku), в том числе для пути MCP, где фабрика сервера молча брала основную модель (small_model_patch.py). Добавлены 16 типов связей с пометкой «исключающая / накопительная» (RUNS_ON, LISTENS_ON … USES, DEPENDS_ON, TRIED_AND_FAILED) — ориентир для разбора противоречий — и тип Publication для книг (имя Document занято rich-моделью MCP).

2. Склейка однофамильцев и нарицательных

«Баранов» — автор пособий по ЕГЭ — приклеился к «Баранову В. Н.» — подрядчику из другого проекта; слово «банк» — к Альфа-банку. Механизм тот же: дедуп без наших правил плюс сущности из нарицательных слов. В инструкцию извлечения добавлено: нарицательные без имени — не сущности; людей называть с ролью («Пётр Баранов (автор пособий ЕГЭ)»); план помечать словом «план», не выдавать за сделанное; неудачную попытку извлекать как TRIED_AND_FAILED с причиной. Уже склеенные карточки разведены по провенансу: у каждого факта есть список эпизодов-источников, рёбра с «чужими» эпизодами перевешены на отдельную карточку (split_node.py). Скан сводок дешёвой моделью (mixed_scan.py, 8 центов на 2,6 тысячи карточек) нашёл 39 кандидатов, почти все — мусорные узлы, а не склейки смыслов.

3. Секреты, которые фильтр пропустил

Две реальные утечки: пароль Wi-Fi роутера (стоял одинокой строкой в блоке кода — ни одна регулярка «пароль: значение» не дотягивалась, а в хранилищах секретов его не было) и пароль gpg-архива (7 цифр — словарь отбрасывал чисто цифровые значения как «не похожие на секрет»). Проверка --check гоняла тот же фильтр по своему выходу — экзаменатор проверял сам себя.

Лечение. Значение из хранилища с секретным именем ключа (PASSWORD, PSK, 2FA, PIN…) — секрет всегда, без проверки «похожести»; новое правило «одинокая строка в блоке кода после слов пароль / password / PSK»; «пароль Wi-Fi сейчас такой: …» с контекстом до двоеточия; сканируются и сводки сообществ; у вырезанных фактов пересчитывается эмбеддинг (иначе поиск по значению всё ещё находил бы факт); самопроверка фильтра с обязательными случаями. Файлы памяти тоже идут через фильтр на хосте (memory_clean.py) — в контейнере словаря нет.

Грабля, найденная grep'ом по снимку

После чистки графа пароль всё ещё лежал в RDB. Оказалось — не в данных, а в потоке telemetry{main}: FalkorDB сохраняет тексты последних запросов, включая наши проверочные с паролем-литералом. Правило: значения секретов никогда не подставлять в текст Cypher-запроса, сверять на стороне клиента; чистка — DEL telemetry{main} перед SAVE. Ещё две мелочи оттуда же: docker exec без -i не передаёт stdin (скрипт из heredoc молча выполняется пустым), а сравнение дат строкой в Cypher (n.created_at >= '…Z') ненадёжно — парсить в Python.

Дайджесты сессий вместо сырых транскриптов

Сырые транскрипты давали 70 % фактов графа и тащили петли «решили → переделали → решили». Решение владельца: граф должен помнить итог и тупики, а не ход. Ночной крон теперь для каждой завершённой сессии (файл не менялся ≥ 2 ч) строит дайджест сильной моделью по жёсткой форме — тема, решения и результаты, тупики с причиной, открытые вопросы, правила владельца — и грузит 1–4 куска вместо 30–140 (session_digest.py, ≈7 центов за сессию, по одному дайджесту на версию сессии). Прогноз: 5–8 долларов в месяц вместо 50.

Метрики после каждой докачки

Главное, чего не хватало: не «поиск выглядит нормально», а числа. metrics.py считает по фактам прогона: быстрые погашения дедупом (окно < 1 дня при найденном факте-погасителе; норма < 5 %), однодневные окна из извлечения, нарицательные карточки, хабы по степени, токены и доллары по моделям (учёт свой — массовая загрузка идёт мимо прокси). Выход за норму — сообщение в Telegram. Плюс пост-шаг: однодневные окна у всего, что прогон погасил, снимаются (для давнего факта обе даты из одного дня — это пересказ, не смена состояния).

Ремонт уже собранного графа вместо пересборки

Литература в таком случае склоняется к пересборке («системное загрязнение промптом»), но решающий критерий — обратимость: у нас сохранены эпизоды и провенанс каждого ребра. Ремонт: repair_invalidations.py снял invalid_at у 3,9 тысячи фактов по правилу (окно < 1 дня и есть погаситель), ещё у 1,8 тысячи после проверки Sonnet («могут ли оба быть верны одновременно?», 1,5 доллара) и у 2,5 тысячи однодневных из извлечения; 8,2 тысячи погашений без погасителя — история из текста — не тронуты. Итог: 17,7 → 9,7 тысячи фактов с invalid_at. Проверка на копии графа перед этим (GRAPH.COPY + обязательно выставить group_id копии всем узлам и рёбрам, иначе дедуп «не видит» старые карточки): быстрые погашения 4,1 % против 13–21 % до патча.

Сверка с практикой

Совпало с тем, что пишут о графах из текста: правила надо класть в промпты дедупа, недосклейка лучше пересклейки, нарицательные — через онтологию, метрики качества после загрузки, засвеченные пароли ротировать, а не только вырезать. Из литературы добавили типы связей с исключительностью и «дайджест как дедуп на уровне утверждения». Perplexity при этом уверенно сослался на апстрим-фикс «invalidate only edges the new edge could plausibly replace» — проверили по коду: промпт байт в байт наш, фикса нет. Поисковый ответ с гладкой формулировкой проверять первоисточником.

Файловая память как Obsidian-хранилище

Сравнение с Obsidian показало: наша файловая память — по сути то же хранилище Markdown со ссылками, и практики советуют держать её источником истины, а граф — производным индексом. Взят «уровень 1»: в шапке каждой заметки status: confirmed | proposed | paused | obsolete, verified_at, scope; загрузчик кладёт статус в заголовок куска, а смена статуса перезагружает заметку — граф перестаёт выдавать планы за факты и получает invalid_at для устаревших заметок. Приложение Obsidian с синком папки — отдельное решение, пока не принято.
