# Графовая память для Claude на своём сервере — инструкция для коллег

Как мы построили многослойную память на Graphiti + FalkorDB, загрузили в неё ~3,5 тысячи фрагментов заметок
и переписки и какие грабли собрали по дороге. Всё проверено на живом сервере 15 сентября 2026; цифры настоящие.
Стек: Graphiti MCP 1.29 / graphiti-core 0.30.x · FalkorDB 4.20 · Claude Code + MCP · OpenRouter.

## Зачем и что получилось

У ассистента уже была файловая память: markdown-заметки, которые он читает в начале сессии. Она мгновенная
и надёжная, но плоская: нет поиска по смыслу, нет связей между объектами, нет понимания, что факт устарел.
Хотелось второй слой поверх файлов.

Graphiti (getzep/graphiti, Apache-2.0) строит из текста **темпоральный граф знаний**: карточки-сущности,
факты-рёбра между ними, у каждого факта две даты — с какого момента он верен и с какого перестал. Модель нужна
только при записи; поиск работает на эмбеддингах, полнотексте и обходе графа без модели. Есть готовый MCP-сервер,
так что Claude Code видит граф как набор инструментов.

Что в итоге лежит в графе: 36 файлов памяти боевого сервера, 254 файла памяти старого сервера, 49 транскриптов
сессий за июнь–июль и 38 транскриптов с боевого сервера. Около 3,5 тысяч фрагментов, 9 тысяч карточек, 27 тысяч
фактов. Стоимость загрузки — около 30 долларов вместе со всеми пилотами и неудачными попытками; повторная загрузка
с нуля стоила бы 15–20.

## Итоговая архитектура

| | |
|---|---|
| контейнер `graphiti-mcp` | образ `zepai/knowledge-graph-mcp`: FalkorDB + MCP-сервер в одном. Порты только на 127.0.0.1: 6379 (база), 8000 (MCP, endpoint `/mcp` без слэша), 3001 (веб-просмотр графа). |
| модель извлечения | `google/gemini-2.5-flash-lite` через OpenRouter. Читает фрагмент, выдаёт карточки и факты по JSON-схеме. |
| модель дедупа | `anthropic/claude-haiku-4.5` — то, что graphiti-core зовёт `small_model`. Решает «эта карточка уже есть?» и «этот факт противоречит старому?». |
| эмбеддер | BAAI/bge-m3 (1024 измерения). Для массовой загрузки — через OpenRouter, для повседневной работы MCP — локальный контейнер TEI на CPU. Векторы идентичны. |
| граф | **Единый граф `main`** = группа по умолчанию MCP (`group_id`); в FalkorDB каждая группа — отдельный граф. Связи и устаревание работают только внутри одной группы — поэтому одна. |
| загрузчики | Свои скрипты на graphiti-core (`add_episode_bulk`), минуя очередь MCP: 12 фрагментов за порцию, 60 потоков, патч с векторным индексом. |
| наши правки | Ни одной строчки внутри Graphiti не менялось. Всё — monkeypatch поверх (см. «Скорость») и обёртки. Патч откатывается на штатное поведение при ошибке. |
| конфиг | Всё серверное — в `graphiti-memory.yaml` (скилл `graphiti-memory`); скрипты общие для всех серверов. |

## Установка

1. **Compose.** Один сервис из готового образа, порты привязать к 127.0.0.1, том для данных базы включить в ночной
   бэкап. Каталог со своими скриптами монтировать *как каталог* (`./scripts:/app/loaders:ro`), не отдельными файлами.
   В скилле compose генерируется из конфига: `gm_config.py render-compose`.
2. **config.yaml MCP.** Провайдер LLM — `openai` с `OPENAI_API_URL` OpenRouter: для неофициального URL graphiti берёт
   совместимый клиент через chat.completions. Родной клиент anthropic в образе сломан (лишний аргумент `temperature`).
   Типы сущностей — свои, doc-only: Server, Service, Project, Domain, Incident, Credential, Runbook, Rule, Human,
   Company, Tool. Имена, совпадающие с встроенными (Person, Organization, Document…), подтягивают rich-модели
   и по отдельному вызову модели на каждую карточку — в семь раз дороже.
3. **Телеметрия выключена** (`GRAPHITI_TELEMETRY_ENABLED=false`), `SEMAPHORE_LIMIT` для MCP — 5–8.
4. **Фаервол.** Помимо привязки к localhost добавить порты в правила ip6tables-DROP: у нас аудит нашёл, что IPv6
   обходил все ограничения.
5. **Регистрация в Claude Code:** `claude mcp add --transport http --scope user graphiti http://127.0.0.1:8000/mcp`.
   Инструменты `mcp__graphiti__*` появятся в новых сессиях.
6. **Учёт расходов.** OpenRouter отдаёт точную цену ответа только с флагом `usage.include`, который Graphiti не ставит.
   Крошечный прокси (`or_proxy.py`) дописывает флаг и пишет цену каждого вызова в JSONL. Для массовой загрузки прокси
   убрали (см. «Скорость»), для MCP оставили — объёмы там малы, а учёт полезен.

## Выбор моделей

Сравнивали на одних и тех же 20 файлах памяти (37 фрагментов) в отдельных группах: цена, число карточек и фактов,
результат читали глазами.

| модель извлечения | $/фрагмент | карточек | фактов | вывод |
|---|---:|---:|---:|---|
| gemini-3.7-flash | 0,20 | 25,6 | 29,7 | чистые имена, но в 7 раз дороже из-за 1,9 млн входных токенов |
| **gemini-2.5-flash-lite** | **0,03** | 24,1 | 50,0 | выбрана: больше фактов, следует правилу об устаревании, шумнее имена — лечится doc-only типами |
| deepseek-v4-flash | 0,002 | 8,5 | 5,6 | рассуждает прямо в именах карточек, выдумывает IP |
| gpt-5.6 (через OpenRouter) | — | — | — | строгая json_schema OpenAI отвергает схему Graphiti |
| claude-haiku-4.5 | 0,023 | — | — | работает, качественно, но дорого для 3 тысяч фрагментов |

> **Что важно знать про Graphiti.** Внутри graphiti-core две роли: основная модель извлекает карточки и факты,
> а `small_model` делает дедуп и инвалидацию. По умолчанию это одна модель. Мы проверили три варианта дедупа
> на тех же 37 фрагментах: flash-lite оставила мусорные «серверы» вроде `eth0` и путей к файлам, gemini-2.5-flash
> наплодила дублей людей, Haiku 4.5 дала самый чистый результат при той же скорости. Итог: дешёвая модель
> на извлечение, Haiku на дедуп.

Что не лечит ни одна модель: «Амстердам», «прод» и «201.51.23.17» так и остаются тремя карточками. Кандидатов
на склейку Graphiti ищет по похожести имён, и такие пары до модели просто не доходят. Для этого нужен пост-проход
по таблице псевдонимов (см. «Качество»).

## Эмбеддер

На один фрагмент Graphiti делает 3–5 вызовов модели и **50–100 вызовов эмбеддера**: каждая карточка, каждый факт,
каждый поисковый запрос дедупа. Поэтому задержка эмбеддера определяет всё.

| вариант | задержка | вердикт |
|---|---:|---|
| qwen3-embedding-8b через OpenRouter | 1,8 с | первые загрузки шли по 180 с на фрагмент — из-за него |
| bge-m3 через OpenRouter | 0,4–0,5 с | выбран для массовой загрузки; хвосты до 136 с режутся таймаутом |
| bge-m3 локально, TEI на CPU (6 ядер) | 40 мс в покое | для MCP отлично; под массовой загрузкой очередь 3–4 с, отдаёт 429, лимит 32 текста на запрос |

> **Грабля.** Локальный и облачный bge-m3 дают одинаковые векторы (косинус 1,0000 на проверке), их можно смешивать
> в одном графе. А вот смена модели эмбеддера — это другое пространство координат: граф придётся перезалить целиком.

## Скорость: где на самом деле тормоз

Утренняя загрузка шла по 200–490 секунд на порцию из 12 фрагментов и замедлялась с ростом графа; к вечеру те же
порции шли за 80–120 секунд и не зависели от размера. Между этими цифрами — пять находок.

### 1. У драйвера FalkorDB в graphiti-core нет векторного индекса

Драйвер создаёт только range- и fulltext-индексы. Каждая проверка «есть ли похожая карточка» — это
`vec.cosineDistance` в WHERE по всем узлам группы: полный перебор, 120–140 мс на запрос при 3 тысячах фактов,
десятки запросов на фрагмент. База ела 3–8 ядер, порции росли линейно с графом. Это видно в `GRAPH.SLOWLOG`.

FalkorDB при этом умеет HNSW-индекс из коробки. Патч `falkor_vector_patch.py` лениво создаёт два индекса в графе
группы и подменяет четыре функции graphiti-core на версии с `db.idx.vector.queryNodes` / `queryRelationships`.
Паттерн подсмотрен в форке JeremyErard/sdi-graphiti-service (PR #58). Замер: перебор 140 мс → индекс 1,5 мс.

```
CREATE VECTOR INDEX FOR (n:Entity) ON (n.name_embedding) OPTIONS {dimension:1024, similarityFunction:'cosine'}
CREATE VECTOR INDEX FOR ()-[e:RELATES_TO]-() ON (e.fact_embedding) OPTIONS {dimension:1024, similarityFunction:'cosine'}
```

> **Грабля внутри грабли.** Первая версия патча подменила метод класса `FalkorSearchOperations`. В 0.30.x этот класс
> в пути дедупа не участвует: реальные реализации — функции-модули в `search.search_utils`, реэкспортированные
> по имени в `search.search` и `utils.maintenance.node_operations`. Подменять надо во всех модулях, где лежит
> оригинал. Патч честно отработал вхолостую: индексы не создались, время не изменилось.

> **Грабля: как искать концы ребра.** Первый запрос брал кандидатов из индекса и потом искал ребро по uuid:
> `MATCH (n)-[e:RELATES_TO {uuid: rel.uuid}]->(m)`. FalkorDB на такой связке перебирает все карточки на каждого
> кандидата: 1640 мс, хуже штатного перебора. Правильно — `startNode(e)` / `endNode(e)`: 1 мс. Ровно этот дефект есть
> и в штатном полнотекстовом поиске рёбер graphiti-core 0.30.1 (1040 мс), в 0.30.2 его починили той же формой;
> мы перенесли исправление в патч. Поиск рёбер по списку uuid тоже переписали: `UNWIND $uuids AS u MATCH ()-[e {uuid:u}]->()`
> без меток на концах идёт по индексу (0,7 мс), с метками — 250 мс.

### 2. Загрузчик слал эмбеддинги не туда

В загрузчике памяти база для эмбеддера была взята из переменной для модели. Итог: 20 тысяч вызовов bge-m3 ушли
в облако через прокси вместо локального контейнера, при медиане 0,5 с и одном зависании на 136 секунд, которое
держало всю порцию. Мораль: печатать в логе загрузчика, куда именно идут эмбеддинги (загрузчики скилла печатают).

### 3. Локальный эмбеддер не тянет массовую загрузку

Как только эмбеддинги пошли в локальный TEI, он упёрся в 6 ядер: очередь 3–4 с, при двух загрузчиках 429.
Плюс лимит 32 текста на запрос, а пакетный путь Graphiti шлёт по 35–45 (`embed_chunk_patch.py` режет по 32).
Решение: массовая загрузка — облачный bge-m3 напрямую (`embedder.bulk_api_url`), локальный — только для MCP.

### 4. Прокси без keep-alive

Учётный прокси открывал новое TLS-соединение на каждый запрос: 594 мс против 400 мс у SDK с постоянным
соединением, то есть плюс 30–50 % на каждый из тысячи вызовов на порцию. Массовую загрузку перевели напрямую
в OpenRouter; таймауты (модель 120 с, эмбеддер 20 с) и повторы выставлены в SDK-клиенте, который передаётся
в конструкторы graphiti (`OpenAIGenericClient(client=…)`, `OpenAIEmbedder(client=…)`).

### 5. Потоки, порции, соединения

- 60 потоков (`SEMAPHORE_LIMIT`) с пулом соединений к базе 512 → «Too many connections» на каждой порции.
  Пул нужен 4096 (свой клиент FalkorDB с `max_connections`).
- Порция 25 фрагментов → дедуп-запрос на 600+ карточек, ответ модели за 8 тысяч токенов рвётся, JSON не парсится,
  повторы по кругу, порция не заканчивается никогда. Порция 12 — потолок для flash-lite.
- Больше 60 потоков не помогает: внутри порции параллельность ограничена числом фрагментов. Единственный множитель —
  несколько процессов на разные группы; но в единый граф пишет один процесс (flock).
- После всех правок база почти простаивает (4,5 мс на запрос), а порция — это ожидание сети × последовательные
  фазы Graphiti: извлечение → дедуп карточек → дедуп фактов.

## Загрузка корпуса

Файлы памяти режутся на фрагменты до 2500 символов по границам абзацев; `reference_time` фрагмента = дата изменения
файла (для перевезённого архива — из сохранённого манифеста `{file: {mtime_epoch}}`, иначе всё датировалось бы
днём копирования). В шапке фрагмента — описание файла и, для исторических, баннер «архив, роли серверов действовали
до такой-то даты»: модель переносит это в даты фактов.

Транскрипты сессий Claude Code (JSONL) — только реплики человека и текстовые ответы ассистента: без вызовов
инструментов, их выводов, «размышлений», системных вставок и вставок скиллов (одна такая вставка была на 560 тысяч
символов). Реплики длиннее 40 тысяч символов выбрасываются. Куски режутся по границам реплик, `reference_time` —
время первой реплики куска, в шапке — тема сессии и дата.

> **Инструкция модели** (`custom_extraction_instructions`, в конфиге `instructions.*`): IP, hostname и прозвище одной
> машины — одна карточка; не делать карточек из путей, кодов ошибок, переменных, портов, интерфейсов; значения
> секретов не извлекать; даты вида 14.09 относить к текущему году; ассистента не делать субъектом фактов;
> **invalid_at ставить только при явном «закрыто / больше не / до даты»**. Без последнего пункта модель штамповала
> «устарело» на треть фактов, включая живые.

Идемпотентность: список загруженных имён фрагментов хранится в `state/<граф>.json`; для докачки имя включает хеш
содержимого (`файл#3@a1b2c3d4`), так что изменённый кусок грузится заново, а прежняя версия остаётся историей.
На граф — один загрузчик (flock): два писателя плодят дубли.

## Фильтр секретов

Транскрипты полны токенов, паролей и строк подключения в выводах команд. Перед загрузкой каждая реплика проходит три слоя:

1. **Словарь реальных значений**, собранный с самого сервера (`secrets.files`: env-файлы, ключи, приватные ssh-ключи,
   JSON с credentials). Около 200 значений, живут только в памяти процесса. Точное совпадение → `[REDACTED:known]`.
2. **Регулярки по форматам**: ключи OpenRouter/OpenAI/Anthropic, токены Telegram-ботов, JWT, Google, VK, вебхуки Bitrix,
   PEM-блоки, `user:pass@` в URL, Bearer, KEY=VALUE с секретным именем ключа, телефоны.
3. **Энтропия**: длинные (≥24) высокоэнтропийные токены без пробелов и точек.

Проверка — повторный прогон фильтра по выходу (`sessions_extract.py --check`), ожидается ноль. Пять итераций правок
ушло на ложные срабатывания: имена файлов памяти вида `project_x_2026-07-11`, слово «passport» как «pass»,
кириллические описания из комментариев в env, имена ботов после слова «токен», имена моделей `vendor/model`.

> **Грабля.** Фильтр стоял на транскриптах, а память старого сервера считалась чистой (секреты из неё вынесли заранее).
> После склейки карточек в сводке «Владелец» всплыл телефон старого Telegram-аккаунта. Второй инструмент —
> `scrub_graph.py` — прогоняет тот же фильтр по содержимому графа (сводки, факты, тексты эпизодов) с записью
> обратно: исправлено 213 полей, среди них 24 телефона, ключ IndexNow, старые вебхуки, строки подключения.
> Правило: **любой источник — через фильтр, после загрузки — контрольный прогон по графу**.

## Качество и пост-проходы

**Хорошо:** факты датированы временем сессии или файла; инфраструктурные факты точны («IP двойника нужно добавить
в allow-list прокси», «на proxy2 включён парольный SSH»); история проекта восстанавливается по датам.

**Лечится пост-проходом** — `merge_aliases.py`: таблица псевдонимов (IP ← прозвища, хосты, Tailscale-адреса;
«Владелец» ← имя, ник, chat_id; «Claude Code» ← Claude, Ассистент), IP с портом или /32 → голый IP (кроме
127.0.0.1 и 172.17.0.1, где порт — разные сервисы, и кроме подсетей /24), одинаковые имена одной метки без учёта
регистра. Рёбра перевешиваются с копией всех свойств (`SET r2 = properties(r)` сохраняет и uuid, и векторы),
упоминания из эпизодов переносятся, сводки склеиваются, дубль удаляется. Перед боевым прогоном — `GRAPH.COPY`
и проверка на копии. У нас: перевешено 2812 рёбер, потерянных ссылок из эпизодов ноль.

**Остаётся:**
- Доля фактов с `invalid_at` 20–37 %. Это не только модель: Graphiti гасит старый факт при появлении похожего нового
  (темпоральное вытеснение), для истории это правильно. При поиске смотреть на даты, а не отбрасывать.
- В транскриптах ассистент местами остаётся субъектом («Claude Code выявил…»).
- Файл памяти про саму эту систему даёт мета-факты («домен распознан graphiti как сущность») — такие файлы
  исключаются (`sources.memory.exclude`).

## Единый граф `main` вместо семи групп

Утром группы дробили ради скорости (дедуп без индекса перебирал все факты группы). После индекса это потеряло смысл,
а вред остался: карточка сервера лежит в каждой группе своя, связи не пересекают границу, устаревание между
источниками не ставится. Механическая склейка семи графов это не лечит — штампы «устарело» и слияние по смыслу
появляются **только в момент записи в тот же граф**, когда библиотекарь видит все карточки.

Решение — один граф `main` (группа по умолчанию MCP: `add_memory` и поиск без `group_ids` идут в него). Порядок сборки
(`build.steps`): самый большой уже загруженный блок берётся копией графа одной командой (`GRAPH.COPY` + перекраска
`group_id` + копия state — экономит часы и доллары), дальше хронологически: старые транскрипты → память боевого
сервера → его транскрипты → инбокс. После каждого блока — таблица псевдонимов, в конце — контроль секретов.
Один писатель, порция 12, 60 потоков. Старые группы после приёмки удаляются (после снимка `backup.sh`), крон и поиск — на `main`.

После сборки обязательно два прохода руками. Первый — **добивка**: порции, на которых модель после всех повторов
вернула битый JSON (у нас 10 из 233 — при этом сторож видел одну, остальные строки ошибок проглотил фильтр лога), в state не попадают; `fixup.sh` прогоняет загрузчики по тем же файлам и
подхватывает только их. Второй — **прозвища**: выгрузить из графа имена карточек `Server` и `Human`
(`MATCH (n:Server) RETURN n.name`), дописать варианты в `aliases` и прогнать склейку ещё раз. Дешёвая модель
плодит «Амстердам-dev», «Амстердам (будущий dev)», «Aмстердам» латинской A, «старом dev», «двойник Алматы»,
логин e-mail владельца как отдельного человека — дедуп по похожести имён этого не видит. Мусорные `Server`-узлы
(адреса Telegram, подсети 10.x, числовые id серверов у провайдера) — известный дефект; лечится инструкцией
извлечения, склейка их не трогает.

### Патчи нужны и MCP-серверу

Первый же поиск по собранному `main` из сессии Claude Code (7,6 тыс. карточек, 33 тыс. фактов) висел дольше двух
минут, один поток FalkorDB ушёл в 100 %, база перестала отвечать даже на `PING`, а контейнер пришлось жёстко
перезапускать. Причина та же, что и у медленных загрузок утром: патчи с индексом стояли только в загрузчиках,
а MCP-сервер — отдельный процесс того же venv — искал штатным кодом graphiti-core 0.30.1: полный скан по
косинусу плюс полнотекстовая связка с перебором карточек на каждого кандидата. На маленьких группах это было
терпимо, на едином графе — нет.

Лечение: `scripts/sitecustomize.py` в `/app/loaders` и три переменные в compose — `PYTHONPATH=/app/loaders`,
`GRAPHITI_PATCH=1`, `VECTOR_INDEX=1`. Python подхватывает `sitecustomize` при старте любого процесса, патч
подменяет те же функции, что и у загрузчиков. Результат: `search_memory_facts` 0,2 с, `search_nodes` 1,3 с.
Проверка после каждого пересоздания контейнера — `docker logs … | grep falkor_vector_patch`.

> **Грабля при перезапуске.** RDB на 360 МБ грузится около минуты, и всё это время `redis-cli ping` отвечает
> `LOADING` с кодом возврата 0. Штатный стартовый скрипт образа принимал это за готовность, запускал MCP-сервер,
> тот падал на первом запросе, контейнер уходил в рестарт — и загрузка RDB начиналась заново, по кругу
> (`RestartCount` рос на глазах). Свой `start-services.sh` ждёт именно строку `PONG`; он монтируется поверх
> штатного и указан как `entrypoint`. И второе: `docker restart` контейнера, в который был примонтирован
> **один файл**, упал с «mount … not a directory» — файл на хосте к тому времени переехал, а на его месте
> Docker создал каталог. Выход — `docker compose up -d` с актуальным compose; файлы монтировать только там, где
> без этого нельзя (`config.yaml`, `start-services.sh`), и не двигать их.

## Эксплуатация

- **Поиск в сессии:** `search_memory_facts` и `search_nodes` (граф по умолчанию `main`); факты идут с `valid_at`/`invalid_at`.
  Запись в конце сессии — `add_memory` одного-двух выводов, полминуты и копейки.
- **Ночная докачка** кроном (`cron_load.sh`): изменённые файлы памяти, транскрипты сессий, не менявшихся ≥2 часов,
  тексты из inbox-бота; после — склейка псевдонимов и контроль секретов; в Telegram — только при ошибках.
- **Сторож долгих загрузок** (`chain_watch.sh`): раз в две минуты живость процесса, застой более 10 минут, новые
  ошибки порций; раз в 20 минут сводка. Загрузка идемпотентна, перезапуск теряет одну порцию.
- **Добивка** (`fixup.sh`): после сборки или докачки с `!! batch` в логе — повторный прогон по тем же файлам, грузятся
  только сорванные порции (state идемпотентен), затем склейка и контроль секретов.
- **Снимок перед разрушительным** (`backup.sh`): `redis-cli SAVE` и копия `dump.rdb` (права 600) в каталог снимков с
  ретенцией — перед `GRAPH.DELETE`, `clear_graph`, пересозданием контейнера, сменой эмбеддера. Правило владельца:
  сначала снимок, потом действие; путь снимка и команда отката — в отчёт. Том FalkorDB дополнительно в ночном rclone;
  граф в любой момент можно снести и пересобрать из источников.

> **Две грабли про сам сервер.** Bind-mount одного файла в Docker держит старый inode: после правки редактором
> контейнер видит прежнюю версию. Монтировать каталог. И второе: правка работающего bash-скрипта не действует —
> файл меньше 8 КБ bash читает в буфер при старте целиком. Наш цикл «три группы параллельно» так и запустил две.
> Перезапускать.

> **Четыре грабли про сторожа и логи** (все всплыли на сборке `main`). Фильтр предупреждений graphiti
> (`grep -v "…|Unterminated|…"`) глотал и строку `!! batch N ошибка: Unterminated string…` — сторож честно
> сообщал «ошибок 0», а порция была потеряна; теперь строки `!! batch` пропускаются всегда, фильтруется остальное.
> Лог с выводом модели становится для grep «бинарным» — без `-a` grep молча возвращает пустоту, и сторож объявляет
> застой на живой загрузке. Переменную со списком state назвали `GROUPS` — это встроенный массив bash, счётчик
> показывал «0=». И `pkill -f run_fixup.sh`, выполненный из оболочки, в командной строке которой было то же имя,
> убил саму оболочку — убивать по PID через `pgrep -f "[r]un_fixup"`. Перезапущенный сторож начинал счёт ошибок с
> нуля и повторно алертил старую — теперь стартует с текущего значения в логе.

## Все грабли одним списком

1. Родной клиент anthropic в образе MCP сломан → OpenAI-совместимый путь через OpenRouter.
2. Встроенные имена типов сущностей включают rich-модели → отдельный вызов на карточку, в 7 раз дороже. Свои doc-only имена.
3. Удалённый эмбеддер с задержкой 1,8 с → 180 с на фрагмент. Задержка эмбеддера решает всё.
4. Инструкция «устарело → invalid_at» слишком буквальна → треть фактов проштампована. Только при явных словах.
5. Нет векторного индекса у драйвера FalkorDB → перебор, база ест ядра, порции растут с графом. Патч с HNSW.
6. Патч подменил не тот класс → работал вхолостую. Подменять функции во всех модулях-импортёрах.
7. Поиск ребра по uuid после индекса → 1640 мс. startNode/endNode → 1 мс. Тот же дефект в штатном fulltext 0.30.1.
8. Эмбеддинги памяти шли в облако через прокси по ошибке в переменной.
9. Локальный TEI на CPU: 429 и лимит 32 текста на запрос при массовой загрузке.
10. Прокси без keep-alive: +30–50 % на вызов. Напрямую, таймауты в SDK.
11. 60 потоков и пул 512 → Too many connections. Пул 4096.
12. Порция 25 → ответ дедупа рвётся по лимиту вывода, бесконечные повторы. Порция 12.
13. RediSearch: Syntax error в полнотекстовом запросе роняет всю порцию → оградить, отдавать пустой список.
14. Bind-mount файла держит старый inode; правка работающего bash-скрипта не действует.
15. Дубли «прод / IP / город» не лечит ни одна модель → таблица псевдонимов.
16. Секреты в «чистой» памяти → фильтр на всё и контрольный прогон по графу.
17. Мелкие группы ради скорости → швы между графами. С индексом размер группы не важен → один граф `main`.
18. Патчи стояли только в загрузчиках → MCP-сервер на едином графе искал сканом, поиск >120 с, FalkorDB завис. `sitecustomize` + `GRAPHITI_PATCH=1` в compose.
19. Стартовый скрипт образа принимал `LOADING` за готовность → цикл рестартов и вечная загрузка RDB. Свой `start-services.sh`, ждать `PONG`.
20. Bind-mount одного файла, который на хосте переехал → `docker restart` падает «not a directory». Каталоги; `compose up -d`.
21. Фильтр служебных строк глотал `!! batch … Unterminated` → сорванная порция невидима. Пропускать `!! batch` всегда; `fixup.sh`.
22. Лог «бинарный» для grep без `-a`; `GROUPS` — встроенный массив bash; `pkill -f` по имени убивает свою оболочку; сторож после рестарта алертит старое.
23. Модель плодит варианты имён одной машины, дедуп по похожести их не видит → после сборки выгрузить Server/Human, дописать `aliases`, склеить ещё раз.
24. Перед любым разрушительным — снимок (`backup.sh`), иначе откат невозможен без владельца.
